## 4. 旧案との違い

一般ユーザーが1問クリア後に投稿する案、投稿者の解答数を信用点にする案、天候推薦、自治体ごとの独立ラリー、ログイン後付けの匿名プレイ案は採用しない。過去の添付資料にこれらがあっても、本リポジトリの最新仕様に戻す。

過去の「仕様v0.2」でGoogleログインが未決だった箇所はD-07で更新済み。クラウド案v0.1は実設定ではない。現在の小規模なVertex AI試験はD-13を参照し、クレジット適用と本番構成は未確認として扱う。

ユーザーの明示決定により、問題詳細（T02）から挑戦（T04の撮影・GPS送信）へ進む導線を端末で役割分担する。PCの位置情報は精度が足りず、現地で撮影する前提に合わないため、PCでは挑戦導線が物理的にほぼ成立しない。一方でPCの強みは大きな地図・写真・記録の閲覧にある。実装は次のとおり。ビューポート幅981px以上（ワークスペースが2カラムになる境界と一致。UA判定はしない）を「広い画面＝PC」とし、詳細の主ボタンを「スマホで挑戦する」に置き換えて、その問題の詳細を直接開くURLのQRコードを表示する。従来の挑戦ボタンは副次的なボタンとして残し、このPCから挑戦を始める到達可能性は維持する（判定はサーバー側で端末に依存しない）。狭い画面では従来どおり「挑戦を始める」系のボタンが主導線のままで、表示も変わらない。QRコードの生成は端末内だけで完結し、URLを外部サービスへ送らない（生成には `qrcode` パッケージを使う）。

あわせて、問題の詳細を直接開けるディープリンクを正式な遷移として扱う。URLの `?area=<地域ID>&quest=<問題ID>` で問題を指定でき、開くと読み込み後に該当問題の詳細が表示された状態になる（該当問題が存在しない場合は従来どおり未選択の表示になる）。QRの飛び先は現在のページURLにこの2パラメータを付けたものである。ログインを挟む場合の「元の問題を保持」（T03）など既存の遷移仕様は変更しない。サーバー・APIの変更はない。

## 2026-11-08: 地域に標準の市区町村コードを持たせる（D-30）

ユーザーから「地域に地方区分ベースの番号を付けると処理が楽になるのでは」という提案があった。独自番号は新設せず、管理側の所在地（D-23）と国土数値情報 N03 で既に使っている標準の市区町村コード（5桁）を、公開探索地域の任意項目 `municipalityCode` として持たせる形を採る。標準コードであれば、並び順が北から南になり、地方の導出や自治体との照合もそのまま賄える。実装は D-22 の `prefectureCode` と同じ流儀で、サーバーの公開投影は保存値が5桁数字の場合だけ応答に含め、共有パーサーは契約として検証する。デモ地域では単一コードのある9件（札幌市 01100／仙台市 04100／郡山市 07203／横浜市 14100／京都市 26100／大阪市 27100／広島市 34100／福岡市 40100／那覇市 47201）に投入し、特別区23区の結合である東京と未分類の demo-area には投入しない（未設定が正しい）。今回は「持たせる＋公開射影まで」を範囲とし、並び順や地方グルーピングにコードを使う箇所の置き換えはしない。

## 2026-11-08: 問題番号（都道府県コード＋連番）を付ける（D-31）

謎に人間が読める番号を持たせ、会話・案内・運用で指し示せるようにする。形式は都道府県コード（2桁）＋「-」＋連番（2桁ゼロ埋め）で、例えば福岡の1問目は「40-01」になる。市区町村コード方式では特別区の東京が抜けるため、都道府県コード方式を採る。番号は公開時にサーバー側で確定して問題ドキュメントへ保存し、以後に問題が増えても既存の番号は動かさず、休止・再公開でもその問題の番号を維持する。下書きには番号を持たせない。連番は、その都道府県コードを持つ地域に属する公開済み問題の中での通し番号（1から）とし、都道府県コードごとのカウンタドキュメントを公開トランザクションの中で更新して重複させない。都道府県コードが無い地域（未分類の demo-area 等）の問題には番号を付けない。公開 API の問題の射影と管理側の ManagedQuest に任意項目 `questNumber` として含め（保存値が妥当な場合のみ）、旅行者側の問題カードと詳細、管理画面の一覧に小さいラベルで表示する。既存の公開済み11問のうちコードのある10問は各都道府県の1件目として「-01」をバックフィルし（判定に使うスナップショットには触れない）、demo-area の1問は番号なしのままにする。
